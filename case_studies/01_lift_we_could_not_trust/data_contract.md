# Data contract: Case 01

All timestamps are UTC. The experiment clock starts 2026-03-02T00:00:00Z (a Monday). Every table is written by `abf simulate case01`; the manifest at `data/manifests/case01.json` records seed, parameters, row counts and a content checksum per table.

| Table | Grain | Keys | Columns and types | Event definition | Source |
|---|---|---|---|---|---|
| users | one row per eligible user | user_id (int64, unique) | platform (str: ios, android, web); app_version (str: 8.1 to 8.6, or "web"); country (str); pre_period_orders_28d (int32) | attributes as of first eligibility | simulated |
| assignments | one row per assigned user | user_id | arm (str: control, treatment); assigned_at (datetime, tz-aware) | first checkout-page request, when the hash bucket is evaluated | simulated |
| exposures | one row per render event | event_id (int64, unique); user_id | exposed_at (datetime); widget_version (str: v1 control, v2 treatment) | the checkout widget's render event as received by the analytics pipeline; none for users served the server-rendered fallback | simulated, with incident |
| checkout_attempts | one row per load of the payment step | user_id (non-unique) | attempted_at (datetime); payment_step_error (bool: the load raised a client error); latency_ms (float, NaN when the widget timing event is absent) | one row per load of the payment step, at least one per eligible user, through the widget or, for users served the fallback, the legacy checkout; a load is a visit to the payment step and is not a payment, so most loads end without an order; latency comes from the widget's timing event | simulated |
| orders | one row per order | order_id (int64, unique); user_id | ordered_at (datetime); received_at (datetime); amount (float); refunded_at (datetime, NaT when not refunded) | completed order; received_at is when the batch pipeline delivered it; refunded_at is within 14 days of ordered_at | simulated |
| telemetry_health | one row per platform × app_version × day | platform, app_version, day | users (int, users whose widget rendered); event_loss_rate (float) | 1 − logged render events / server-side widget renders, arms pooled | simulated monitoring table |
| truth | one row per user | user_id | p_control, p_treatment (float; equal for users served the fallback); y0, y1 (int8); rendered, exposure_logged, in_affected_cell (bool) | potential outcomes, render and incident flags | simulated; written for audit and read by no analysis (the operating-characteristic runner computes the same quantities in memory) |

Time semantics: `ordered_at` is when the order happened; `received_at` is when it became visible to analysis. The outcome window is 7 days from `assigned_at`. Data is complete at experiment end + 7 days + 36 hours (2026-03-24T12:00Z).

Joins (seed 20260928): assignments ⟕ users on user_id (280,000 rows, none unmatched); assignments ⟕ exposures on user_id (233,889 users with an event; 46,111 assigned users without one: about 15% of each arm served the fallback, plus about 4,200 treatment users on Android below 8.4 whose render event was lost); assignments ⟕ checkout_attempts on user_id (364,031 payment-step loads, every user at least one); orders ⟕ assignments on user_id (8,990 orders, one per converter, none unmatched).

Known missingness: no widget render for 15% of eligible users in both arms, who are served the legacy fallback (`non_render_probability`; arm-independent and expected; these users cannot be affected by the widget, so their two potential outcomes are equal). Server-side renders exist only as the aggregate counts behind `telemetry_health`; there is no user-level server render log. Render events lost with probability 0.35 for rendered treatment users on Android below 8.4, drawn at random within that cell (differential by arm; the incident; `incident.affects_arm` accepts treatment, control or both). Refunds land up to 14 days after the order, so the refund guardrail is incomplete for orders placed in the 14 days before any analysis clock. Order arrival delay uniform on 0 to 36 hours in both arms (non-differential). Latency missing exactly where the render event is missing, which includes every load served by the fallback.

Data-generating constants (module-level in `checkout_incident.py`, not sourced from any real product; change them and rerun): platform shares 0.40 / 0.40 / 0.20 (iOS, Android, web); app-version shares 0.04 to 0.30 rising with version; conversion logit offsets +0.30 iOS, −0.30 Android, −0.30 additional for versions below 8.4 (config key `affected_cell_logit_offset`), +0.25 per log(1 + pre-period orders); intercept calibrated so the control rate is exactly the configured 3.2%; pre-period orders zero-inflated negative binomial (structural zeros 0.70 plus a negative binomial with mean 2.0 and dispersion 0.8, whose own zero probability is 0.37, so 81% of users outside the affected cell have no pre-period order; 0.78 and 1.6 for Android below 8.4, giving 87%); payment-step error 4% per load; latency log-normal (median 1,200 ms, sigma 0.35); time from first eligibility to order exponential (mean 20 h, truncated to the 7-day window); amount log-normal (median 48, sigma 0.60); refund probability 5% per order, uniform over 14 days, identical by arm. Assignment is a hash of user id with a salt drawn from the seeded generator and recorded in the manifest (`realised.hash_salt`). Each block of the generator (covariates, arrival times, assignment salt, rendering, outcomes, render-event loss, order timing) draws from its own random stream, and every per-user quantity is drawn by inverse CDF from a fixed number of uniforms per user, so a parameter change moves only what depends on it. Config values are validated on load, with an error naming the key.

Manifest: `data/manifests/case01.json`.
